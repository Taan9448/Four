3. **일상 명령 예시와 수동 경로** — 이슈를 넘길 때 쓰는 짧은 명령, 그리고 ChatGPT 채팅에서 이미지만 만들 때의 절차입니다.

## 1. AGENTS.md 본문

````markdown
# AGENTS.md — Codex 작업 규칙(아트 전용)

이 저장소는 무협×판타지 소설 「천외귀환」을 원작으로 한 브라우저 덱빌딩 게임이다.
두 AI가 나눠서 개발한다. 코드·데이터·문서는 Claude Code가, 그래픽 에셋은 너(Codex)가 만든다.
사람(저장소 주인)은 이슈를 너에게 넘기고, Claude Code가 아트 PR을 검토·머지한다.

## 1. 범위

- 네가 수정할 수 있는 곳은 **`assets/source/`와 `assets/sprites/` 두 폴더뿐**이다.
- `specs/`, `src/`, `data/`, `tools/`, `docs/`, `assets/placeholders/`, 설정 파일, 워크플로는 수정하지 않는다. CI가 소유권을 검사하므로 다른 파일이 바뀌면 PR이 실패한다.
- 코드·스크립트·명세에 문제가 있으면 고치지 말고, PR 본문의 "발견한 문제" 칸에 적는다.
- `assets/manifest.json`은 만들지도 커밋하지도 않는다(빌드 때 생성됨).

## 2. 먼저 읽을 것(우선순위 순)

1. 이 파일(AGENTS.md)
2. 이슈 본문: 명세 경로, 선행 에셋, 완성 프롬프트, 참조 이미지 경로
3. `specs/assets/<id>.yaml`: 규격의 단일 기준. 이슈 본문과 다르면 명세를 따른다.
4. `docs/ART_STYLE.md`: 화풍, 팔레트, 캐릭터 외형
5. `docs/ASSET_PIPELINE.md`: 시트 규격 전체

## 3. 작업 순서

1. **선행 에셋 확인.** 명세의 `depends_on`에 적힌 에셋이 `main`의 `assets/sprites/<dep>/meta.json`으로 존재하는지 확인한다(`npm run assets:status`의 마지막 열). 없으면 작업하지 말고, 이슈에 "선행 에셋 <dep> 대기"라고 댓글을 남기고 멈춘다.
2. **브랜치 생성.** 최신 `main`에서 `art/<이슈번호>-<id>`를 만든다.
3. **준비.** `npm ci`(처음 한 번), `npm run assets:prompt -- <id>`로 완성 프롬프트를 확인한다. 이슈 본문의 프롬프트와 같아야 한다.
4. **생성.** 내장 이미지 생성(`$imagegen`)으로 **시트 한 장**을 만든다.
   - 프롬프트는 완성 프롬프트를 그대로 쓴다. 재시도 때만 끝에 "Fix:" 문장을 덧붙일 수 있다.
   - 명세의 `reference`(기준 시트)가 있으면 반드시 참조 이미지로 첨부한다.
   - 결과는 `assets/source/<id>.png`에 저장한다.
   - 실제로 쓴 프롬프트 전문(덧붙인 Fix 포함)은 `assets/source/<id>.prompt.txt`에 저장한다.
5. **자르기와 검증.** `npm run assets:slice -- <id>` → `npm run assets:validate -- <id>`
6. **눈으로 확인.** `assets/sprites/<id>/_contact.png`와 `_preview.gif`를 직접 열어 본다.
   - 얼굴·머리·의상·색·무기·크기가 모든 프레임에서 같은가
   - 기준 시트와 같은 인물인가
   - 동작이 frame_notes 순서대로인가
   - 바라보는 방향이 명세의 `facing`과 같은가
   - 잘린 팔다리·무기가 없는가
7. **재시도와 대체.** 검증이나 눈 확인에서 실패하면 **최대 2회** 다시 생성한다. 그래도 안 되면 대체 단계로 내려간다(4절). 생성은 한 번에 시트 하나씩 한다(사용 한도 절약).
8. **커밋.** `assets/source/<id>.png`, `assets/source/<id>.prompt.txt`, `assets/sprites/<id>/**`를 커밋한다. 메시지는 `art(<id>): <한 줄 요약>`.
9. **PR.** 아트 PR 템플릿(`.github/PULL_REQUEST_TEMPLATE/art.md`)으로 연다.
   - 라벨: `codex`
   - 본문: `Closes #<이슈번호>`, 사용한 대체 단계, 검증 결과 요약, 재시도 횟수, 발견한 문제

## 4. 대체 단계(fallbackLevel) — 프레임끼리 모습이 어긋날 때만

| 단계 | 방법 | 언제 |
|---|---|---|
| 1 | 전체 프레임 시트(기본) | 처음 |
| 2 | 키 포즈 3장(준비·타격·회복)만 그린 시트. 나머지는 게임이 보간 | 1단계를 2회 재시도해도 **프레임끼리 얼굴·의상·크기가 어긋날 때** |
| 3 | 머리·몸통·팔·무기를 분리한 파츠 시트. 게임이 관절 애니메이션 | 2단계도 같은 이유로 실패할 때 |

- **대체 단계는 프레임 불일치만 해결한다.** 다음 경우에는 쓰지 않는다.
  - **기준 시트(character-ref)**: 항상 전신 2칸(1단계)만. 파츠 시트는 기준이 될 수 없다.
  - **격자 문제**(픽셀 격자 일치도 실패, 격자 감지 실패, 흐림): 대체 단계로 해결되지 않는다. 재시도 2회 후에도 실패하면 **멈추고 PR 본문(또는 이슈 댓글)에 원본과 측정값을 남겨 Claude에게 넘긴다.**
- 2단계 시트: 같은 캔버스·격자에서 칸 1~3에 준비·타격·회복 포즈만 그리고 나머지 칸은 비운다. 완성 프롬프트의 `Frames:` 부분을 이 3칸으로 바꿔 쓰고, 바꾼 전문을 `<id>.prompt.txt`에 남긴다.
- 2·3단계는 `npm run assets:slice -- <id> --fallback 2`(또는 3)로 자르고, `npm run assets:validate -- <id>`로 검증한다.
- 단계는 meta.json의 `fallbackLevel`에 기록되고, PR 본문에도 쓴다.

## 5. 시트 규격 요약 — 64 그림 격자 · 80 프레임 픽셀 아트(자세한 것은 docs/ASSET_PIPELINE.md)

전투 그래픽은 **칸당 64×64 그림 격자로 그리는 픽셀 아트**다(사람형 캐릭터 키 약 48px). 너는 큰 캔버스에 **"확대된 픽셀 아트"**를 그린다.
게임 프레임은 그보다 큰 **80×80**이라, 도끼를 치켜드는 동작이나 칸을 꽉 채운 그림도 줄이지 않고 담는다. 너는 지금처럼 64 격자로 그리면 된다.
요청 블록은 8×8 px이지만, **자르기 도구가 그림에서 실제 블록 크기와 격자 위치를 자동 감지**하므로 정확히 8px이 아니어도 된다.
대신 **모든 블록이 같은 크기로, 한 개의 곧은 격자 위에** 있어야 한다. 모델이 더 굵은 블록(예: 칸당 48px)으로 그리면 그 해상도 그대로 80 프레임에 담긴다.

| type(size) | 캔버스 | 격자 | 칸 | 그림 격자 → 프레임 | 요청 블록 | 배경 |
|---|---|---|---|---|---|---|
| character-anim (small) | 1536×1024 | 3×2 | 512×512 | 64 → 80 | 8×8 | 명세의 chroma(마젠타 #FF00FF 또는 초록 #00FF00) |
| character-anim (large, 보스) | 1536×1024 | 3×2 | 512×512 | 128 → 160 | 4×4 | 명세의 chroma |
| character-ref (small) | 1024×1024 | 2×2 | 512×512 | 64 → 80 | 8×8 | 명세의 chroma. 칸1 3/4 정면, 칸2 측면, 칸3·4 빈칸 |
| fx (small) | 1536×1024 | 3×2 | 512×512 | 64 → 80 | 8×8 | 검정 #000000(빛나는 효과만) |
| background | 1536×1024 | 1 | — | 384×256 → 384×256 | 4×4 | 풀 배경(전투 배경) |

- 한 시트는 최대 6프레임(3×2). 모든 캐릭터 칸이 512px이라 시트마다 캐릭터 크기가 고르게 나온다.
- **이미지 크기가 규정과 달라도(예: 1254px) 리사이즈하지 말고 그대로 저장한다.** 비율만 맞으면 도구가 원본에서 격자를 감지한다.
- 블록보다 작은 디테일, 안티에일리어싱, 흐림, 그라데이션, 반투명은 금지.
- 색은 `docs/ART_STYLE.md`의 마스터 팔레트(32색) 안에서, 스프라이트 하나에 16색 이하(이펙트 12색 이하).
- 외곽선은 1블록(=스프라이트 1px) 두께의 짙은 남색 `#1d2433`.
- 프레임(칸) 번호는 1부터, 왼쪽→오른쪽, 위→아래 순서다.
- 사람형 캐릭터는 약 48px 키(칸 높이의 약 3/4), 발의 가장 아래 픽셀은 64줄 중 58번째 줄, 가로 가운데. 칸 가장자리 5px는 비운다. 칸을 위아래로 꽉 채우지 않는다.
- 자르기 도구가 발을 80 프레임의 72번째 줄에 맞춘다.
- 격자선·테두리·글자·숫자·워터마크는 금지. frames 이후 칸은 순수 배경색.
- 배경색과 같거나 비슷한 색을 캐릭터에 쓰지 않는다.
- 검증기는 블록 격자를 감지하고 "픽셀 격자 일치도"를 잰다. 격자를 못 찾거나 50% 미만이면 실패, 65% 미만이면 경고.

### 5-1. 이야기 갈래 — 애니메이션 채색 일러스트(픽셀 아님)

카드 일러스트·초상화·스토리 장면·캐릭터 설정화는 **픽셀 아트가 아니다.** 선이 살아 있는 손그림 애니메이션 채색 일러스트 한 장으로 그린다(`docs/ART_STYLE.md` 2-1절).

| type | 캔버스 | 게임 출력 | 배경 |
|---|---|---|---|
| card-art | 1024×1536 | 512×768 | 풀 배경 |
| portrait | 1024×1024 | 512×512 | 부드럽게 칠한 단순 배경 |
| story-cg | 1536×1024 | 1152×768 | 풀 배경 |
| character-sheet | 1536×1024 | 원본 | 밝은 종이색 단색 |
| character-standing | 1536×1024(3×1칸) | 칸마다 512×1024 | 마젠타 #FF00FF 단색(자를 때 투명으로) |

- 격자·팔레트 규칙이 없다. 자르기 도구는 출력 크기로만 줄인다. 검증은 크기·비율 위주다.
- **character-standing(반신 그림)**: 비주얼 노벨 장면과 영웅·전설 카드 컷인에 쓴다. 칸1 기본·칸2 결의·칸3 놀람 표정의 **같은 인물을 같은 크기·같은 위치**로, 머리 꼭대기부터 허리까지. 배경은 마젠타 단색이고 인물에 마젠타·분홍·보라를 쓰지 않는다(배경을 지울 때 함께 지워진다). 테두리 선을 깔끔하게.
- 같은 인물은 그 캐릭터의 설정화(character-sheet)가 있으면 반드시 참조 이미지로 첨부한다.
- 글자·로고·서명·테두리 금지. 프롬프트에 특정 스튜디오·작가 이름을 넣지 않는다.

## 6. 이미지 모델이 자주 틀리는 것(생성 전후 점검)

- **픽셀 아트처럼 보이지만 실제로는 부드러운 그림**(블록 경계가 흐림) → "solid square blocks", "no anti-aliasing" 강조해 재시도
- **블록 크기가 칸마다 다르다**(어떤 칸은 48px, 어떤 칸은 64px 해상도처럼 보임) → "SAME size on ONE straight grid" 강조
- 칸 사이에 격자선이나 테두리를 그린다 → 프롬프트의 Rules 문장 확인
- 칸마다 캐릭터 크기가 다르다 → 키(약 48px)와 발 위치(58번째 줄)를 강조해 재시도
- 배경에 그라데이션·바닥·그림자를 넣는다 → "flat solid" 강조
- 팔레트 밖의 색이 많다 → 자르기 도구가 맞춰 주지만 색이 뭉개지므로 팔레트 문장을 강조
- 칸에 번호나 글자를 써 넣는다 / 무기·머리카락이 칸 밖으로 나간다
- 측면이어야 할 프레임이 정면 3/4로 돌아간다 / 빈 칸이어야 할 곳에 포즈를 하나 더 그린다
- `_contact.png`는 80×80 프레임으로 바꾼 결과를 확대해 보여 준다. **바꾼 결과에서** 얼굴·무기가 읽히는지 확인한다.

## 7. 피드백 반영(needs-fix)

- PR에 `needs-fix` 라벨과 Claude의 프레임별 댓글이 달리면, 같은 브랜치에서 지적된 내용을 "Fix:" 문장으로 덧붙여 다시 생성한다.
- 자르기·검증을 다시 실행하고 같은 PR에 푸시한다.
- 지적이 명세와 충돌하면 고치지 말고 PR 댓글로 묻는다.

## 8. 하지 말 것

- 1절 범위 밖의 파일 수정(명세의 오타 수정 포함)
- 프레임을 한 장씩 따로 생성해 이어 붙이기(일관성이 깨짐)
- 검증 실패를 무시하고 PR 올리기. 실패한 채 올려야 한다면 PR 제목에 `[검증 실패]`를 붙이고 이유를 적는다.
- 참조 이미지 없이 애니메이션 시트 생성(ref 자체를 만들 때만 예외)
- 기존 `assets/source/` 원본을 다른 에셋 작업에서 덮어쓰기

## 9. 화풍 시험(haun_ref)

- 전투 화풍은 **64 격자 픽셀 아트**(게임 프레임 80)다. 외곽선·명암·얼굴 같은 세부는 첫 에셋 `haun_ref`로 시험한다.
- 주인공 하운은 긴 흑발, 날카롭고 차분한 눈매, 숯빛 긴 겉옷의 어두운 차림이며 무기는 벌목용 도끼다(`docs/ART_STYLE.md` 4절).
- `haun_ref` PR이 머지되기 전에는 하운의 애니메이션 시트(#3, #4)를 처리하지 않는다(`depends_on`으로도 막혀 있다). `fx_slash_blue`, `wolf_ref`는 독립이라 먼저 진행해도 된다.
````

## 2. Codex 첫 지시(앱·CLI에 처음 한 번 붙여 넣기)

```
너는 이 저장소(taan9448/four, 「천외귀환」 덱빌딩 게임)의 아트 담당이다.
코드는 Claude Code가 맡고, 너는 그래픽 에셋만 만든다.
이 게임의 그래픽은 두 갈래다.
- 전투(캐릭터·적·이펙트): 64×64 프레임 픽셀 아트. 큰 캔버스에 "확대된 픽셀 아트"(논리 픽셀 1개 = 정사각형 블록 하나)를 그리면
  자르기 도구가 실제 블록 크기를 감지해 64×64 프레임에 담고 마스터 팔레트에 맞춘다.
- 이야기(카드 일러스트·초상화·스토리 장면·설정화): 선이 살아 있는 손그림 애니메이션 채색 일러스트 한 장.

1. 저장소 루트의 AGENTS.md를 끝까지 읽고, 그 규칙을 이 세션 내내 최우선으로 따라라.
   이어서 docs/ART_STYLE.md와 docs/ASSET_PIPELINE.md를 읽어라.
2. 읽은 뒤 다음을 짧게 요약해서 보여 줘. 내가 네 이해를 확인하려는 것이다.
   - 네가 수정할 수 있는 폴더
   - 이슈 하나를 처리하는 순서(브랜치 이름, 생성, 자르기, 검증, PR)
   - 에셋 유형별 캔버스·격자·블록 크기·논리 해상도·배경색
   - 픽셀 아트 규칙(블록 정렬, 팔레트, 외곽선, 금지 사항)

   - 대체 단계 1~3과 넘어가는 조건, 그리고 대체 단계를 쓰지 않는 경우
3. 그다음 asset-request 라벨이 달린 열린 이슈 목록을 보여 주고,
   depends_on 때문에 지금 처리할 수 없는 이슈를 구분해 줘.
   아직 아무 이슈도 처리하지 마라. 내가 번호를 지정하면 그때 시작한다.
```

## 4. 수동 경로 — ChatGPT 채팅에서 이미지만 만들 때

Codex가 이미지 생성을 못 하는 환경이거나, ChatGPT 채팅에서 직접 그리고 싶을 때 씁니다.

1. 이슈 본문의 **완성 프롬프트 전문**을 복사합니다.
2. ChatGPT 새 채팅에 다음을 보냅니다. 참조 이미지(예: `assets/sprites/haun_ref/` 또는 `assets/source/haun_ref.png`)도 함께 첨부합니다.

   ```
   아래 프롬프트를 한 글자도 바꾸지 말고 그대로 사용해서 이미지 한 장을 생성해 줘.
   첨부한 이미지는 같은 캐릭터의 기준 시트야. 스프라이트 디자인·색·비율·픽셀 크기를 정확히 맞춰 줘.
   캔버스 크기는 프롬프트에 적힌 크기 그대로, 픽셀 블록은 프롬프트에 적힌 크기의 정사각형으로 격자에 맞춰 그려 줘.
   부드러운 일러스트가 아니라 블록이 또렷한 픽셀 아트여야 해.

   <완성 프롬프트 붙여 넣기>
   ```

3. 결과를 내려받아 `<id>.png`로 이름을 바꿉니다.
4. Codex에 이렇게 맡깁니다(이미지 파일을 함께 전달):

   ```
   이 파일을 assets/source/<id>.png로 넣고, 이슈 #N을 AGENTS.md 3절의 5단계(자르기)부터 진행해.
   프롬프트는 이슈 본문 것을 그대로 assets/source/<id>.prompt.txt에 저장해.
   ```
